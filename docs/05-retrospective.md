# 05 复盘：最难的问题、收获与下一步

## 1. 最难的问题

### 1.1 把「冲突不擅自选」变成可执行的状态机

题目里最容易被写成一句 prompt（「遇到冲突要问用户」）的要求，实际需要工程化：

- 什么算冲突？同一属性、多个文档、取值不同。还要排除「同一文档的分档标准」（5/10/15 天）、
  「一个文档是另一个的超集」这类假冲突。
- 查证是什么？不是再搜一次关键词就完了，要识别 `memo/notice` 类型的制度解释、解析「以《X》为准」、
  再确认被指定文档的原文已经读过。
- 追问之后怎么办？用户说「按最新版本」时，要把选择落到具体 `doc_id`，读原文，再回答，
  并在答案里保留另一方取值，否则审计会判定「冲突未说明」。

最终把它拆成：`detect_conflict` → `_conflict_flow`（查证检索 → 读解释 → 解析优先级）→ `_clarify_payload` / `_answer_resolved`，
并用 02 / 09 两个场景固定下来。这个过程让我意识到：**可信不是提示词风格，而是状态与证据链**。

### 1.2 证据判定的假阳性

`D01-4.3` 只是引用了《票据遗失与替代凭证处理说明》，却因为出现「遗失」被当成证据，
导致系统引用了一份「说要去看另一份文件」的条款。修复是剔除 `《…》` 后再判断。
这个 bug 很典型：检索分数高、关键词命中、引用也逐字，**但引用不支持结论**。
如果没有「读到原文后再判断是否真的回答」这一步，系统看起来完全正常。

### 1.3 审计与「模型说了算」的边界

真实模型可能给出漂亮但编造的引用。只靠 prompt 约束不可靠，所以把审计做成确定性代码：
逐字比对 + 冲突取值是否全部出现；不通过就把状态降级为 `audit_failed`，并写明「不可采信」。
`tests/test_audit.py` 用回放决策模拟了「编造引用」和「擅自选 15 天」两种模型输出，都能被拦下。
代价是严格：模型把引用改写一个标点也会失败——但这是有意的取舍。

### 1.4 预算与「继续查」的张力

07 场景里为了确认没有可读证据，Agent 把 8 次工具调用全部用在了 D09/D01/D02 的重复读取上；
这既证明了「持续失败会停」，也暴露了策略可以更省：同一文档连续失败后应减少重试、优先换候选。
08 场景则说明预算必须**在执行前**检查，否则「读取成功但没预算记录」会让 Trace 不可信。

### 1.5 阈值不是拍脑袋

最初的阈值（3/5 分）会让无关文档也进入证据链；用 `scripts/inspect_retrieval.py` 打印实际分数后，
才把「可信 15 / 改写 30 / 无意图 60」定下来。分数会随语料变化，所以脚本和校准方法一并提交，
而不是只留一个魔法数字。

## 2. 学习收获

- **可验证性优先**：先定义「什么算答对」（引用逐字、冲突说明、状态），再写代码；
  比先写 Agent 再想怎么测有效得多。
- **把模型当不可信组件**：模型输出只是「建议」，工具执行、预算、审计必须是代码。
- **Trace 是产品的一部分**：每步的决策依据、参数、返回摘要、后续动作，既方便调试，也是评审材料。
- **Mock 的边界要写清楚**：Mock 能证明流程，不证明效果；不写清楚就是误导。
- **小语料也能暴露大问题**：8 篇文档就能暴露引用假阳性、分档正则、审计漏项。

## 4. 下一步（按收益排序）

1. **接真实模型并做对照评测**：同一批场景分别跑 Mock / GPT-4o-mini / 本地模型，
   比较「引用支持率」「冲突识别率」「无效工具调用数」。
2. **混合检索**：BM25 + 向量 + rerank，补充同义词表覆盖不到的口语问法；
   把「检索改进」从规则改写升级为模型改写 + 效果回退保护。
3. **冲突知识库**：把「哪些条款互相冲突、由谁解释」沉淀成结构化数据，
   让 `ask_user` 能一键升级为归口部门工单。
4. **评测集扩充**：按业务域、问法、冲突类型、工具故障类型分层，加入对抗性问法（越界、诱导、多跳）。
5. **会话与权限**：多轮 Session、用户所属部门/职级过滤文档适用范围（本项目的 `applies_to` 目前只用于展示和冲突说明）。
6. **可观测性**：Trace 落盘到结构化日志、指标（工具失败率、追问率、审计失败率），接入告警。
