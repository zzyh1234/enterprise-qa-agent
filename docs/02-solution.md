# 02 方案与动态决策

## 1. 总体架构

```
                    ┌────────────────────── CLI / batch / verify ──────────────────────┐
                    │  run.py ask / batch / verify / corpus                             │
                    └───────────────────────────────┬─────────────────────────────────┘
                                                    │
                                    ┌───────────────▼────────────────┐
                                    │      KnowledgeQAAgent          │
                                    │  预算(步数/工具调用) + 审计降级  │
                                    └───────┬────────────────┬───────┘
                                            │                │
                              PlannerInput  │                │  ToolResult
                                            │                │
                    ┌───────────────────────▼──┐      ┌──────▼─────────────────────┐
                    │ Planner（可插拔）          │      │ KnowledgeTools             │
                    │ ・MockPlanner（离线/回退）   │      │ ・search_docs（BM25+改写）  │
                    │ ・OpenAI 兼容（默认）        │      │ ・read_snippet（逐字原文）  │
                    │ ・Replay（回放决策）        │      │ ・故障注入（error/empty）   │
                    └───────────┬──────────────┘      └──────┬─────────────────────┘
                                │ Decision                   │
                                └──────────► 循环 ◄───────────┘
                                            │
                                ┌───────────▼─────────────┐
                                │ 审计 audit.py           │
                                │ 引用逐字 + 冲突是否说明   │
                                └───────────┬─────────────┘
                                            │
                                AgentResult(status/answer/citations/trace)
```

分层原则：**工具只取资料、决策器只出动作、Agent 只管循环与预算、审计只管一致性**。
真实模型与离线 Mock 走完全相同的循环、工具、审计与预算，只是「决策来源」不同。

## 2. 一次问答的生命周期

1. CLI 加载语料、意图规则、同义词表，构造 `RetrievalIndex`（片段级 BM25）。
2. Agent 初始化 `Budget(max_steps, max_tool_calls)`、`KnowledgeTools`（含故障注入）。
3. 循环：
   - 若步数用尽 → 返回 `incomplete_budget_exceeded`；
   - 构造 `PlannerInput`（问题、历史、上一轮结果、已执行观察、剩余预算）；
   - Planner 输出一个动作：`search_docs` / `read_snippet` / `ask_user` / `finish`；
   - 工具动作先检查工具调用预算，再执行，把「参数 + 返回摘要」写入 Trace；
   - `finish` / `ask_user` → 组装结果、跑审计、结束。
4. 审计：每条引用逐字比对原文；引用之间若存在取值冲突，答案必须提到全部取值，否则降级为 `audit_failed`。

## 3. 决策器的动作契约

| 动作 | 参数 | 触发时机（Mock 规则 / 真实模型） |
| --- | --- | --- |
| `search_docs` | `query`, `top_k`, `use_expansion` | 首轮检索；置信度低时改写检索；发现冲突时查证制度解释 |
| `read_snippet` | `doc_id`, `section_id` | 命中后必须读原文才能引用；读完发现答非所问则换片段/换文档 |
| `ask_user` | `question`, `options`, 冲突取值与引用 | 冲突无法在语料内消解、需要用户指定适用制度 |
| `finish` | `status`, `answer`, `citations`, `gaps`, `conflicts` | 已有可核验证据且无未解决冲突；或明确资料不足/工具失败/超预算 |

真实模型必须输出严格 JSON；`parse_decision` 会校验动作与必填参数，非法输出会让 Agent 记录
`planner_error` 并给模型一次纠正机会（`max_planner_retries=1`），仍失败则 `failed`。

## 4. 动态决策的两条典型路径（来自实际 Trace）

### 路径 A：冲突 → 查证 → 追问（`examples/02`）

| 步骤 | 决策依据 | 动作 | 观察 | 后续 |
| --- | --- | --- | --- | --- |
| 1 | 首轮检索，不预设答案 | `search_docs` 原问题 | 最高分 7.30（D01）、5.90（D02），低于改写阈值 30 | 改写检索 |
| 2 | 置信度低，补同义词后重检 | `search_docs` + `use_expansion` | D02 57.97、D01 50.17 | 读 D02 |
| 3 | 读命中片段核实是否直接回答 | `read_snippet D02-3.1` | 15 天，命中「报销/提交/天」证据 | 读 D01 |
| 4 | 另一篇候选也要核实，避免漏掉冲突 | `read_snippet D01-4.2` | 30 个自然日 | 发现冲突 |
| 5 | 冲突不能擅自选，先查证制度解释 | `search_docs` 「报销时限 制度解释 不一致 以 为准」 | 没有制度解释类文档 | 追问 |
| 6 | 无法在语料内消解 | `ask_user` | 列出 30/15 与两份引用、给出选项 | 结束 |

### 路径 B：同一问题、语料新增制度解释（`examples/09`）

前 5 步与路径 A 相同，第 5 步查证检索命中 D03（memo，32.78 分），随后：

| 步骤 | 决策依据 | 动作 | 观察 | 后续 |
| --- | --- | --- | --- | --- |
| 6 | 命中制度解释类文档，读取确认优先级 | `read_snippet D03-1.1` | 「以《费用报销操作指引（2024 版）》为准」 | 冲突可解 |
| 7 | 已有优先级规则与可核验原文 | `finish(answered)` | 引用 D03 + D02 + D01，结论 15 天 | 结束 |

对比可见：**同一问题、同一 Planner，仅因语料变化，动作从 `ask_user` 变为「读 D03 → finish」，
答案从「无法给出唯一答案」变为「15 天（依据 D03）」。** 这是审核要点「替换文档内容后核对答案与动作」
的直接证据，对应测试 `test_corpus_change_changes_answer_and_actions`。

## 5. 检索与改写

- 索引粒度：**片段（section）**，索引文本 = `heading + text`；文档分数 = 最佳片段分 + 0.2 ×（次佳两个片段分）。
  这样「先看命中摘要、再读原文」的两步工具设计才成立。
- 切词：英文/数字词 + 中文单字 + 中文二元组（不引入分词依赖）。
  制度文本里「报销时限 / 年休假 / 重新认证」用二元组即可稳定召回。
- 改写：`data/query_expansions.json` 维护口语↔制度用语映射（如「带薪假→年休假」「弄没→遗失/丢失」）。
  改写不是独立工具，而是 `search_docs(query, use_expansion=true)` 的一个参数，Trace 会记录
  `expansion_added` 与 `query_used`，能看出「模型主动改写了检索」。
- 阈值（`MockPlanner` 构造参数，可在测试里覆盖）：

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `min_score` | 15.0 | 低于此分不作为证据、不读原文 |
| `rewrite_threshold` | 30.0 | 低于此分先改写检索，避免漏召回 |
| `intentless_min_score` | 60.0 | 问题不属于任何已知意图时，只有极高置信才允许作答 |
| `max_candidates` | 3 | 每轮最多核实的文档数（控制预算） |
| 每文档最多读片段 | 2 | 最佳片段答非所问时再试一个 |

校准依据来自 `scripts/inspect_retrieval.py`（本次实际输出）：

| 场景 | 原查询最高分 | 改写后最高分 | 决策 |
| --- | --- | --- | --- |
| 01 VPN 重新认证 | 44.31（D05-3.1） | —（已高于 30，不触发改写） | 直接读原文 |
| 02 报销期限 | 7.30（D01-4.2） | 59.07（D02-3.1） | 改写后再读，避免只读到较旧文件 |
| 04 发票弄没了 | 15.75（D09-1.1） | 53.18（D01-4.3）/ 51.33（D09） | 改写后逐片段判断证据 |
| 05 工作六年带薪假 | 25.45（D04-2.1） | 67.17（D04-2.1） | 改写明显提分 |
| 08 云盘上传上限 | 55.18（D06-1.1） | —（已高于 30） | 直接读原文 |
| 10 年会抽奖 | 11.24（D04） | 不触发（无意图） | < 60，判定资料不足 |

## 6. 证据判定：避免「看起来相关」当成「回答了问题」

命中只说明关键词相关；**片段是否回答了问题**需要证据判定：

1. 至少命中一个意图证据词（如「报销 + 提交」），且命中词**不能只出现在《制度名称》引用里**；
2. 若该意图需要数值（天数、元/晚、GB、位数），必须能抽出数值；
3. 不满足则记录「已读取但未作为依据」，继续读下一个片段/文档，或判定资料不足。

这条规则来自一次真实误判：`D01-4.3` 写的是「发票或票据缺失的，按《票据遗失与替代凭证处理说明》执行」，
按朴素关键词匹配会命中「遗失」，但它只是**引用**了另一份文件，真正的流程在 `D09-1.1`。
修正方式是在判定前先剔除 `《…》` 内容，于是 `04` 场景最终引用 `D09-1.1`，而不是错误地引用 `D01-4.3`
（见 `examples/04_receipt_lost_paraphrase/trace.json` 与 `run.notes`）。

## 7. 冲突判定与消解顺序

1. 只比较**已经读到原文并通过证据判定**的片段，避免凭检索摘要臆测冲突；
2. 按文档聚合取值集合（同一文档的分档标准如 5/10/15 天不算冲突；某文档取值集合是其他文档的超集时视为细分）；
3. 集合不同 → 冲突，记录每个取值的原句；
4. 查证：用「主题 + 制度解释 + 以…为准」检索，只接受 `memo/notice` 或摘要含「为准」的文档；
5. 读到解释后用「以《X》为准」解析被指定文档，并要求该文档原文已读取（否则先读）；
6. 仍无法消解 → `ask_user`，列出冲突取值、引用、适用范围与查证结论，绝不默认选新版本；
7. 用户显式选择（文档 ID / 「按最新发布的版本」/ 制度类型关键词）→ 读指定制度原文后作答，
   并在答案中保留另一份文件的取值与 `resolution=user_selected`。

## 8. 审计：对 Mock 和真实模型都生效的硬护栏

| 检查 | 规则 | 不通过时 |
| --- | --- | --- |
| 引用逐字 | 引用去空白后必须是原文子串；文档/片段必须存在 | `status=audit_failed`，答案附加「不可采信」 |
| 冲突说明 | 引用之间若存在不同取值，答案必须包含全部取值 | 同上，并记录 `missing_in_answer` |

审计只作用于 `answered` / `partial`；`needs_clarification` 的答案本身就在列冲突，因此会通过。
这不是「让模型自我评价」，而是**对模型输出的确定性复核**：`tests/test_audit.py` 用回放决策模拟
「模型编造引用」「模型擅自选 15 天」两种情况，均可被拦下。

## 9. 预算与失败处理

- `max_steps`：每次决策（含最终 finish/ask_user）计 1 步；
- `max_tool_calls`：只统计 `search_docs` / `read_snippet`，在执行前检查，超限不再调用工具；
- 工具失败：同一动作原样重试一次；文档连续两次读取失败则跳过该文档；无其他候选时返回 `blocked`；
- 回放决策耗尽、模型连续输出非法 JSON：返回 `failed`，并写明原因。

## 10. 技术取舍

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| 原生实现，不用 LangGraph/ADK | 零依赖、离线可跑、循环/预算/审计全部可见可测；框架本身不加分 | 没有现成的持久化、并行、可视化；本版不需要 |
| Mock 决策器 + 真实模型决策器 | 无 Key 也能复现验收点；真实模型只替换「决策来源」 | Mock 是规则，不能证明真实模型效果，已在 README/评测中标注 |
| BM25 + 同义词改写，不用向量库 | 可解释、可离线、能清晰展示「改写前后分数变化」 | 语义泛化弱，需要维护同义词表；真实生产建议加向量召回 |
| 逐字引用 | 审核要求「引用原文是否支持回答」，逐字最容易被机器验证 | 不能自动接受「语义等价但改写」的引用，需要模型按原文引用 |
| 规则化冲突检测 | 可测试、可解释、不会漏掉数值差异 | 只适用于「可抽取数值/关键词」的属性；通用语义冲突需模型 + 人工 |

## 11. 生产化要补的东西

- 混合检索（BM25 + 向量 + rerank）、文档版本有效期与权限过滤；
- 引用定位到字符区间，前端高亮原文；
- 冲突知识库与归口部门审批流（把 `ask_user` 升级为工单）；
- 真实模型 function calling / 流式输出 / 超时与并发控制；
- 评测集扩充（按业务域、问法、冲突类型分层），线上反馈闭环。
